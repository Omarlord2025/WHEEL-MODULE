# Engineering Standards — wheel_tracker

This file is read automatically at the start of every Claude Code session in this repo and is treated as ground truth. Every new function, feature, or script added here must satisfy this checklist before it's considered done.

## 1. Domain model — read this before touching formulas

See `PRD.md` for the full spec. The short version:

- **Wheel Type** — the spec/master record (shape, material, original dimensions, cost, reorder point). One per "Code" in the legacy sheet, one per real ERPNext Item. Since PRD v10, new Wheel Types are auto-created by `item_variant_hooks.py` from an Item Variant (see below) — don't build a "please fill in Wheel Type by hand" UI flow as the primary path; that's now the fallback for the 63 legacy, non-variant Wheel Types only.
- **Wheel** — one physical wheel (`factory_wheel_code`). Belongs to a Wheel Type via its `wheel_type` field. Lifecycle: In Stock → In Use → Retired. Since PRD v10, `Wheel.name` is always identical to a real ERPNext **Serial No**'s name — never assume a Wheel exists without one, and never write `Wheel.status`/`warehouse` directly from new code; go through `wheel.py`'s functions (see Retirement below), which real Stock Ledger movements also drive via `stock_ledger_hooks.py`.
- **Measurement Event** — a submittable caliper-reading log against a Wheel (`wheel` field, fetching `wheel_type`). This is where wear and cost get computed and rolled up. Blocked entirely for Wheels whose Type has `requires_measurement` unchecked (P-series — see PRD v9) — those use **Wheel Retirement** instead (renamed from Wheel Usability Check in PRD v10): a submittable record that retires a Wheel for real — both in Wheel Tracker's own status and via a genuine Material Issue Stock Entry — not a binary usable/not-usable check anymore. Both doctypes share the "log an event against a Wheel, submit to apply it, cancel to revert it" shape; don't build a third variant of that pattern without checking whether one of these two already fits. Since PRD v11, recording several at once doesn't require the single-record form N times — the **Batch Measurement Entry** Page (`batch_measurement.py`) creates/submits one real Measurement Event per row through this exact same code path; it never reimplements wear/cost logic itself. Since PRD v14, it's driven by a date range, not one Job Card: `get_wheels_used_between(from_date, to_date)` finds every Job Card whose Posting Date falls in range and every Wheel that ever appeared in their `Job Card Wheel` history (reusing the same lookup `derive_job_cards()` relies on — a Wheel shows up even after it's moved to a different Job Card or gone back In Stock), excluding Retired Wheels and any Wheel already measured on or after `from_date`. Don't reintroduce a single `job_card` parameter on `get_wheels_used_between`/`submit_batch_measurements` — job cards are found or derived, never passed in.
- **Since PRD v12, a Measurement Event links to a Job Card *table* (`job_cards`, options `Measurement Event Job Card`), not a single Link field** — auto-derived in `derive_job_cards()` from the Wheel's real `Job Card Wheel` assignment history since its previous submitted event (a Wheel can move across several Job Cards between two measurements), with `job_cost` split equally across every distinct Job Card found. Never reintroduce a singular `job_card` field or pass one into `make_measurement_event()`/`submit_batch_measurements()` — both derive the real set themselves. `job_card_integration.py::update_job_card_wheel_cost()` sums a Job Card's share from this child table (a join query), not `Measurement Event.job_cost` directly.
- **Since PRD v12, crossing 100% consumption auto-creates and submits a real Wheel Retirement, not just a status flip.** `MeasurementEvent.create_auto_retirement()`/`cancel_auto_retirement()` (called from `on_submit`/`on_cancel`, strictly *after* `apply_to_wheel()`/before `revert_from_wheel()`) reuse Wheel Retirement's own `on_submit`/`on_cancel` unchanged — `retire_wheel()` is a no-op there since `Wheel.check_auto_retirement()` already retired the Wheel inside the just-completed `wheel.save()`, so only `create_retirement_stock_entry()` does new work. Never call this logic from inside `Wheel.validate()`/`check_auto_retirement()` itself — that Wheel save is still in progress on the call stack, and creating+submitting a new Wheel Retirement there would recurse into it.
- **Item Template / Item Variant** (ERPNext core, not this app's own doctype) — the real data-entry front door since PRD v10. One template (`GRINDING-WHEEL-TEMPLATE`), six Item Attributes (Shape/Material/Diameter/Inner Diameter/Height/Angle, seeded by `setup/item_variant_setup.py`). Employees generate variants via ERPNext's own native wizard; `item_variant_hooks.py` reacts to `Item.after_insert` and builds the matching Wheel Type. Don't add a custom "create Wheel Type" form as the primary UX — that workflow is intentionally ERPNext-native now.
- **Classification masters** (Wheel Shape, Wheel Geometry, Wheel Material, Wheel Grit, Wheel Concentration, Wheel Bond) — every controlled-vocabulary field on Wheel Type is a Link to one of these, not a Select/free-text field, so shop staff can extend the lists from Desk. Wheel Shape links to a Wheel Geometry (Flat/Straight vs Profiled/Angled), which carries the `requires_correction_factor` flag the formula branches on (the name is legacy — see below for what it actually gates now). Seeded on install/migrate from `setup/seed_master_data.py` — see PRD v3 for what real shapes/materials exist. The one exception: `Wheel.status` stays a Select — the Python state machine branches on those exact three strings, so making it user-editable would let someone rename/delete a status the code depends on.
- Volume formulas live in `wheel_type.py::calculate_wheel_volume()` — it is the single source of truth, used by both Wheel Type (original volume) and Measurement Event (current/worn volume). It takes a `requires_correction_factor` bool (never reintroduce string-matching on shape names to decide the branch): flat/straight shapes use the exact annulus `(pi/4)(D²-d²)H`; profiled/angled shapes walk a `Wheel Type.profile_segments` child table (`Wheel Type Profile Segment`: `angle` + `height` per row) and sum a conical-frustum-ring volume per segment — **not** an empirical scalar correction factor (removed in PRD v6) and **not** a single scalar `angle` field (removed in PRD v7, replaced by the segment table for a possible compound/stepped shape). The schema supports 2+ segments, but every real profiled wheel imported so far (12V9 at 45°, 11V9 at 20°, 1V1 at 45° or 10°) is exactly reproduced by a **single** segment — validated against the real "WHEELS WITH ANGLES" data in PRD v8, all 3 angles solved numerically against real recorded volumes, not assumed. Don't add a second segment to a real Wheel Type without an actual worked example or measurement backing it — the 2-segment path has none yet.
- The "usable volume" 10% floor is configurable (Wheel Tracker Settings), not hardcoded — read it via `get_usable_volume_fraction()`, never inline `0.9`. Since PRD v11 a Wheel Type can override it for itself via its own `usable_volume_floor_percent` — always pass `wheel_type.usable_volume_floor_percent` as `get_usable_volume_fraction()`'s `floor_percent_override` arg (blank falls back to the global Settings value automatically); never call it bare from new code that has a Wheel Type in scope.
- Current/worn volume is **auto-computed**, not operator-confirmed (reversed in PRD v6 — the opposite of what earlier versions of this doc said), via `MeasurementEvent._volume_inputs()` — and the inputs it uses **differ by geometry family** (PRD v8):
  - Flat wheels (1A1/P-series) wear only radially — use the *current* diameter reading with the Wheel Type's constant original inner diameter/height. Validated against 73/78 real FLUTE rows to well under 1%.
  - Single-segment profiled wheels (1V1/12V9/11V9) wear *along the bevel* — diameter, inner diameter, and height all shrink together. Use *this measurement's own* current inner_diameter/diamond_height readings, holding only the Wheel Type's angle constant. Using the flat-wheel model here (Wheel Type constants instead of this event's readings) was tried first and gave 42–68% median error — badly wrong; don't revert to it.
  - Compound/stepped profiles (2+ segments): no real data exists on how current readings map onto a multi-segment chain, so this falls back to the Wheel Type's original segments/height. Known, documented limitation, not a validated model — fix it for real once a real 2-segment Wheel Type exists.
- **Naming (v4/v5):** the whole app was renamed Stone → Wheel, including the database columns (see PRD v5) — `factory_wheel_code`, `wheel_type`, `wheel`, and Job Card's `custom_wheels_used`/`custom_wheel_wear_cost`/`custom_wheel_wear_tab` are the real, current DB fieldnames, not aliases. There is no lingering `stone_*` column anywhere in this app's tables — if you find one in new code, it's a bug, not a deliberate exception.
- **Workspace naming (v13):** the Desk workspace is now named/labelled **Grinding Wheels**, not Wheel Tracker (see `wheel_tracker/wheel_tracker/workspace/grinding_wheels/`) — the app's own name, module (`Wheel Tracker`), and every Python package path stayed `wheel_tracker`/`Wheel Tracker`; only the workspace's user-facing name changed. Renaming a Workspace doc requires a `pre_model_sync` patch (`frappe.rename_doc("Workspace", ...)`, see `rename_wheel_tracker_workspace_to_grinding_wheels.py`) run *before* the fixture file syncs — Workspace JSON is upserted by `name`, not content-hash-checked like DocType JSON, so editing the JSON's name alone creates a new orphan doc instead of renaming in place. Also remember CLAUDE.md's own rule below about bumping `modified` on a second edit to this kind of file.
- **Language toggle (v13) is a session-language switch, not a translation of this app.** The Language Toggle button flips the current user's Desk language between Arabic/English (`language_toggle.py::toggle_language()`), which translates Frappe/ERPNext's own core strings (and flips RTL) via their existing language packs — this app's own custom field labels (Wheel, Factory Wheel Code, Consumption %, etc.) have no Arabic translation file and will stay in English regardless. Adding one is a separate, much larger task (a `.csv`/`.po` translation file covering every custom label) — don't assume the toggle already covers it.
- **Retirement (v9/v10/v12):** goes through `wheel.py`'s `retire_wheel()`/`reinstate_wheel()`/`sync_wheel_warehouse()` — not just for P-series; all three are safe to call on any Wheel from anywhere (no-ops if already in the target state). Three independent callers reach these: **Wheel Retirement**'s own `on_submit`/`on_cancel` (direct, whether filed by hand or auto-created), `stock_ledger_hooks.py` reacting to any real Stock Ledger Entry against that Wheel's serial (indirect — Material Issue, Stock Reconciliation to zero, a Sales/Delivery movement), and — since PRD v12 — **Measurement Event**'s `create_auto_retirement()`/`cancel_auto_retirement()`, which auto-creates+submits a real Wheel Retirement the moment a measurement pushes consumption to 100%, instead of leaving that for a human to notice and file later. All three agreeing is deliberate, not redundant to fix. `Wheel.check_auto_retirement()` (consumption ≥100%) still runs on every save regardless and takes priority — don't try to "fix" a wheel that immediately re-retires itself after `reinstate_wheel()`, it means the consumption is still genuinely ≥100%.
- **`mandatory_depends_on` is not reliable for enforcement in this Frappe version** (confirmed on the old Wheel Usability Check's `retirement_reason` — insert() let a doc through with the condition true and the field empty). Keep the JSON attribute for the UI hint, but also check it explicitly in `validate()`, same as `WheelType.validate_dimensions()` already does for its own fields.
- **Real ERPNext stock integration (v10)** — `Bin.actual_qty` and Wheel Tracker's own counts are meant to genuinely agree now (verified: 135 Wheels "In Stock" == 135 units in `Bin` at Main Store after the opening-stock backfill). Two gotchas found only by testing directly against the real ERPNext functions, undocumented anywhere: (1) a template Item's own `Item Variant Attribute` rows need `numeric_values`/`from_range`/`to_range`/`increment` copied onto them by hand when created programmatically — `Item.validate_variant()` reads these off the *template's* row, not the Item Attribute master, and Desk's own form only does this copy client-side; (2) `erpnext.stock.serial_batch_bundle.SerialBatchCreation` needs `use_serial_batch_fields=1` and an explicit `batches={}` in its args dict or it throws (`AttributeError` on `.batches`, or `LinkValidationError` for any serial that doesn't already exist) — see `serial_stock_utils.py::build_serial_bundle()`, the one place this recipe lives, reused by Material Receipt, Wheel Retirement's Material Issue, and the opening-stock backfill. Never hand-roll a second version of this.
- **`Stock Ledger Entry` only ever gets an `on_submit` hook, never `on_cancel`** — confirmed by reading `stock_ledger_entry.py`: SLEs are append-only and `on_cancel()` always `frappe.throw()`s. A voucher cancellation posts a *new*, sign-reversed SLE that itself goes through `on_submit` — `stock_ledger_hooks.py` already covers reversal this way; don't add a doomed `on_cancel` handler.

## 2. Where new code belongs

| Need | Use | Why |
|---|---|---|
| Pure UI behavior — show/hide fields, defaults, query filters, dialogs | **Client Script** (`public/js`) | Runs in the browser. Never trust it for validation or business rules — it's UX sugar, bypassable from the API. |
| Business logic, data integrity, anything reused across doctypes | **This app** | Real Python, real tests, full query-builder access, background jobs. |

Rule of thumb: if it touches the database beyond a trivial read, or you'll ever want to reuse it, it belongs in the app.

**List view formatting (v13):** overriding how a field renders in a doctype's List View (e.g. `Wheel`/`Measurement Event`'s `consumption_percent` — Frappe's own Percent fieldtype renders as a bare bar with no number, see `frappe/public/js/frappe/list/list_view.js`) goes in `doctype_list_js` (`hooks.py`), setting `frappe.listview_settings[doctype].formatters`, never a monkey-patch of core. Shared formatter logic used by more than one doctype's list (see `public/js/consumption_bar.js`) is loaded once via `app_include_js`, not duplicated per doctype-list file.

**An interactive button embedded directly in a Workspace (v13)** — e.g. the Grinding Wheels workspace's Language Toggle — is a real Frappe core doctype, **Custom HTML Block** (`html`/`script`/`style` fields, rendered in a shadow DOM via `frappe.create_shadow_element`; `script` runs as genuine JS with `root_element` bound to the block's own container). It's a plain document, not DocType JSON, so it has to be created via a `pre_model_sync` patch (see `create_language_toggle_block.py`) — running pre-sync matters here too, since the Workspace JSON's `custom_blocks` table links to it by name and needs the record to already exist when that fixture syncs. Whatever the button's `script` calls should be a small whitelisted method scoped to the calling user's own data (see `language_toggle.py::toggle_language()`, which only ever touches `frappe.session.user`'s own record) — never a generic core method whose permission behavior for a non-admin user hasn't been checked.

## 3. Design principles

- **DRY, always.** Shared logic (volume formulas, usable-fraction lookup) lives in one place and gets imported — never duplicated across Wheel Type / Wheel / Measurement Event.
- **Single responsibility.** Controller methods (`validate`, `on_submit`, etc.) stay thin — call into a named helper, don't inline a wall of logic.
- **Every function gets a docstring** — what it does, its params, what it returns. No exceptions.
- **No business logic in client scripts.** `public/js/job_card.js` only sets query filters — it never decides wear/cost/status.
- **Status transitions go through code, not ad-hoc field writes.** Use `wheel.py`'s `assign_to_job_card()` / `release_from_job_card()` rather than setting `status`/`current_job_card` directly from other modules.

## 4. Performance checklist — run this on every function that touches the database

- [ ] No `frappe.get_doc()` inside a loop over more than a handful of records. Use `frappe.get_all()` with an explicit `fields=[...]`.
- [ ] Never call `frappe.get_all()` without a `fields` list.
- [ ] A single-value lookup uses `frappe.db.get_value()`, not a full document load.
- [ ] Anything that could touch more than ~50–100 records runs as a background job (`frappe.enqueue`), not inline inside a blocking hook.
- [ ] No repeated identical DB calls inside a loop — fetch once (e.g. `stock_entry_hooks.py` batches Wheel Type lookups by item code before looping over rows), reuse the result.

## 5. Testing

Every controller method and helper function gets a `frappe.tests`-based unit test — not just a manual click-through in Desk. Tests live in the matching `test_*.py` file next to the code they cover. Formula tests should assert against the PRD's fitted-formula tolerances (§5.2), not arbitrary numbers.

## 6. Before calling anything "done"

Re-read the new code against section 4. Run `bench --site erpnext run-tests --app wheel_tracker --skip-test-records` and `bench --site erpnext migrate` clean before considering a change finished.

The `--skip-test-records` flag is required in this environment, not optional: our Job Card / Stock Entry tests pull in ERPNext's manufacturing test-record dependency chain, which (in this bench) recurses into a Company/Payment Gateway Account fixture that expects the `payments` app — not installed here — and fails with `DocType Payment Gateway not found` before a single test runs. `--skip-test-records` just skips auto-generating shared `_Test *` fixture records (our own tests build everything they need via `test_helpers.py`), so this has no effect on what's actually being verified.

**Editing a Workspace, Report, Number Card, or Print Format JSON a second time?** Bump its `modified` timestamp in the file, or the edit silently won't sync. Unlike DocType JSON (content-hash checked on every migrate), these doctypes are sync-gated purely by `file.modified <= db.modified` (see `frappe/modules/import_file.py`) — the first sync always works (no DB row yet to compare against), but a second edit with the same or an older timestamp is skipped with no error, no warning, migrate just reports success. Set it to something after the current DB value, e.g. `date -u +"%Y-%m-%d %H:%M:%S.%6N"`, and verify with `frappe.db.get_value(doctype, name, "modified")` before trusting a re-sync happened.

**Added or changed a `doctype_js`/`doctype_list_js`/`doctype_tree_js`/`doctype_calendar_js` hook in `hooks.py` (v13)?** A running site's browsers won't see it until the target DocType's own `modified` timestamp changes — confirmed by reading `frappe/desk/form/load.py::getdoctype()`: the client sends back whatever `modified` timestamp it last cached that DocType's meta under, and the server returns the literal string `"use_cache"` (no docs, no error) whenever that still matches the DocType's current DB `modified`, regardless of whether the actual hook-injected JS content (`Meta.add_code_via_hook()`, embedded as `__js`/`__list_js`/etc.) has changed. Editing `hooks.py` alone never touches the DocType's own `modified` — only an edit to that DocType's own JSON does (schema sync bumps it automatically). If a hook-only change needs to reach browsers that already have that DocType open/cached, bump `modified` on the DocType directly (`frappe.db.set_value("DocType", name, "modified", frappe.utils.now())`, then `frappe.clear_cache(doctype=name)`) rather than assuming a plain page refresh or `bench build`/`migrate` is enough — neither touches this specific client-side cache key. (Verify with `frappe.desk.form.load.getdoctype(name, cached_timestamp=<old value>)` — it should stop returning `"use_cache"`.) Note this is a different, unrelated caching layer from the Workspace/Report bullet above — that one gates the *server's* fixture sync, this one gates what the *client* decides to refetch.
